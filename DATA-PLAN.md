## User-supplied data (primary source)
- Google Takeout / Google Maps export parsed client-side (CSV / GeoJSON), stored verbatim via `bulkImportSpots` in chunks; the whole file goes into the one list the user names in the import panel (a Takeout CSV is one Google Maps list per file). Duplicate rows (same URL, or same name+coordinates) are skipped — except the memo: if the imported row carries a memo that differs from the stored one, the stored memo is overwritten with it (so memo edits made in Google Maps flow in with the next Takeout import). An imported row with no memo never erases a stored memo, and no other field of an existing spot is refreshed. The action returns `{ inserted, updated, skipped }` and the import panel reports memo updates in its completion message. (2026-11-13 follow-up: 「既存スポットのメモ更新も反映するよう直して」)
- Every spot belongs to exactly one list: the list name is stored on the spot, empty values are normalized to 「行ってみたい」, and a migration backfills existing rows. Lists are derived from the spots themselves (no separate list table to orphan).
- Manual entry picks an existing list or types a new custom list name.
- No seed rows in production data; the registry starts empty for the user to import into.

## Real boundary shapes (2026-11-16 follow-up: 「実形で作り直して」)
- Boundary source: JapanCityGeoJson (https://github.com/niiyz/JapanCityGeoJson), per-municipality GeoJSON derived from 国土数値情報「行政区域データ N03」, cached by the chat-side job at `~/workspace/location-trivia/boundaries/{11,12,13}/` (埼玉県・千葉県・東京都, fetched 2026-11-16; provenance in that folder's `SOURCE.md`). The same cache generated the image map `~/workspace/your_files/visited_municipalities_map.png`.
- Build-time processing (script run once at build): some JapanCityGeoJson files flatten a MultiPolygon's parts into one Polygon's ring list (e.g. 市川市・船橋市: the tiny first ring is an exclave, the main body is ring 2), so all rings were re-assembled by containment depth (even = exterior, odd = hole of the smallest containing exterior), then Douglas-Peucker simplified (tolerance 0.0005° ≒ 55 m), coordinates rounded to 5 decimals, designated cities merged from their wards （さいたま市・千葉市）. Result: `client/src/assets/visited-boundaries.ts` — all 180 municipalities of the 3 prefectures keyed `${都道府県}|${市区町村名}` (593 KiB), so any future municipality in the home prefectures paints its real shape with no further plumbing. Verified by rendering the asset back to a PNG and comparing against the reference image map: all 28 shapes match, including the 市川市・船橋市 coastlines.
- Stored geometry: `visited_municipalities.geometry` (migration 0007, JSON text of a simplified GeoJSON Polygon/MultiPolygon). `addVisitedMunicipality` accepts an optional `geometry` argument — new rows store it; for an already-recorded municipality it backfills only when the row has none (never overwrites, never moves the first-visit date); calls without the argument behave exactly as before. `importVisitedMunicipalities` accepts the same optional per-entry geometry with the same backfill rule. `listVisitedMunicipalities` returns the parsed geometry.
- Fill resolution order on the client: stored row geometry → bundled boundary asset → circle at the representative point (only for municipalities with no shape anywhere, e.g. a future municipality outside the 3 cached prefectures recorded without geometry).

## Ledger row tap → map fly-to (2026-11-16 follow-up)
- Follow-up requests (verbatim): 「タップしたらそこの地図に飛べるようにしたいかな」 + supplement: 対象は塗りつぶし地図の下にある市区町村リストの各行。行をタップしたら地図がその市区町村のポリゴンの範囲に合うよう移動・ズーム（フライ）し、一時的に強調表示。削除ボタンを押したときは飛ばない。
- Behavior: tapping a ledger row scrolls the map into view, flies the camera to the municipality's boundary bounds (`fitBounds`, padding 36, maxZoom 15, ~1.2 s animation, instant under prefers-reduced-motion; point-only municipalities fly to a small box around the representative point), and emphasizes it temporarily (~4.5 s): an orange focus overlay (fill + 3px outline, or a ring for point-only rows) added at runtime as the `visited-focus` source/layers, plus the row's `map-focused` style and orange pin number. The emphasis clears itself; tapping another row retargets it.
- Delete guard: the row's delete / confirm / cancel controls carry `data-map-no-fly`; both the React row handler and the `mountPlaceListMap` row listener in `map-helpers.mjs` ignore clicks from inside such a control, so deleting never flies.
- Fallback (interactive map unavailable): the row tap scrolls the static map image into view and applies the same temporary row emphasis; no camera move is possible there.
- Local runtime patch: the stock HatchMaps handle only exposes `selectPlace`, which highlights a pin but never moves the camera, so this artifact's bundled copy `client/src/assets/hatch-maps.js` carries a minimal patch to the mount handle adding `getMap()` / `fitBounds()` / `flyTo()` passthroughs to the underlying MapLibre map (one snippet in the `lD` factory's returned object). `client/src/map-helpers.d.mts` declares the extended handle as `PlaceListMapHandle` / `MapLibreLike`. If the runtime asset is ever re-copied from the platform original, this patch must be re-applied or the fly-to silently degrades to row emphasis only (the client polls for the map and no-ops when it never appears).

## Focus highlight geometry-type fix (2026-11-16 follow-up: 「謎の大量の円が現れて消える」)
- Bug: tapping 千葉市 (a merged-ward MultiPolygon) showed a giant blob of overlapping orange circles instead of its boundary shape. Cause: the three `visited-focus` layers shared one source with NO geometry-type filter, and MapLibre's circle layer draws a circle at every vertex of any geometry — a detailed MultiPolygon has hundreds of vertices, so the "ring for point-only municipalities" layer painted the whole shape as stacked circles. (Simple Polygons showed it far less, which is why it read as MultiPolygon-specific.)
- Fix: each focus layer now carries a geometry-type filter — fill + outline layers match only `Polygon` / `MultiPolygon` (`["in", ["geometry-type"], ["literal", […]]]`), the circle layer matches only `Point`. Polygon and MultiPolygon municipalities are always emphasized with their real boundary (translucent orange fill + 3px outline); the circle is used solely for point-only municipalities, never as a substitute for a known shape.

## Focus highlight, second fix + persistent highlight (2026-11-16 follow-up: 「まだ治ってないw」)
- The geometry-type filter fix above did NOT hold on the real device: 鎌ケ谷市 (a plain single Polygon) still rendered a circle at every vertex. Verified at this build: the filter expressions were present verbatim in the shipped bundle, the geometry reaching the focus source is the real Polygon (bundled asset entry `千葉県|鎌ケ谷市` is `{"type":"Polygon", …}`), and the bundled MapLibre v5.24 engine does implement the `geometry-type` expression — yet the circle layer still painted polygon vertices on device. Rather than fight the filter path further, the separation is now STRUCTURAL: two focus sources, `visited-focus-polygon` (fill + outline layers) and `visited-focus-point` (circle layer), with no filters at all. `setFocusGeometry` routes a known boundary exclusively to the polygon source and a representative point exclusively to the point source, clearing the other each time, so the circle layer can never see a polygon.
- Spec change (user's words: 「選択したら空白や他のとこタップするまでハイライトのままでいいよ」): the ~4.5 s auto-clear is gone. The highlight (map geometry + row emphasis + orange pin) persists until another ledger row is tapped (highlight moves), the map's empty area is tapped (map `click` listener; a press that turned into a drag is excluded by comparing the camera center at press start vs. click time, so panning does not clear it), the focused row is deleted, or — in the static-fallback case — the fallback map image is tapped.

## Map-tap row scroll, verify-and-correct (2026-11-16 follow-up: 「そこまでスクロールしてくれないww」)
- Bug (device video): tapping a painted municipality highlighted it and started scrolling the ledger, but the scroll stopped partway — the target row never came fully into view (a single fire-and-forget smooth `scrollIntoView({block:"nearest"})` is cut short when layout shifts mid-animation — the tapped prefecture group is still expanding, the map's focus layers land — and "nearest" could park the row at the very bottom edge, half under the fixed bottom tab bar).
- Fix: the pending row scroll now runs a verify-and-correct loop (`scrollRowFullyIntoView` in App.tsx). It scrolls with `block: "center"`, then re-measures the row's real rect every 120 ms; the row counts as arrived only when it sits fully inside the viewport above the tab bar (bottom ≤ innerHeight − 96). Whenever the scroll has settled (scrollY unchanged for 2 ticks) without the row being there, it scrolls again — instantly, so the correction cannot be cut short the same way. The loop stops when the row arrives, after ~3 s of corrections, when the highlight is cleared / another row is tapped (sequence counter bumped in `clearFocus` / `focusMunicipality`), or when the reader scrolls by hand (touchmove / wheel cancels). Reduced-motion still gets instant scrolls throughout.

- Diagnosis (three compounding causes, per the consultation the reader asked for — separate the basemap's success from the tiles'/overlays', and retry a transient failure once):
  1. The runtime fetches the style with a plain `fetch` (no timeout, no retry) and routes ANY failure to `onFatalError`; its error classifier treats a map error as non-fatal only when it carries a source/tile reference or an HTTP status > 0, so a network-level failure (status 0 — a dropped connection on a weak signal) is classified FATAL. One hiccup during the initial load tore the whole map down.
  2. The app's stall watchdog judged success by `isStyleLoaded()` alone, which in MapLibre stays false until every pending tile and source settles — on slow 4G the fitted view's initial tile set legitimately exceeds the 15 s budget, so healthy still-loading maps were destroyed by the watchdog.
  3. No automatic retry existed anywhere; the only recovery was the manual 「地図を再読み込み」 button.
- Fix (App.tsx only; the bundled runtime, both fallbacks, all data and actions untouched):
  - `watchBasemapLoad` now takes `onLoaded` as well as `onTimeout`, and "basemap arrived" means the map's `load` event (style loaded + first frame rendered), with `isStyleLoaded()` kept as the backstop for a load event that fired before the watcher first saw the map. Tile/overlay completion no longer gates the verdict.

The manual reload buttons also reset the retry budget.
  - Once a mount's basemap has arrived (`mapLoadedRef`, set by the watchdog's `onLoaded`; reset at each mount's start so every mount re-earns it), later error callbacks are ignored and the live map stays mounted — at that point a "fatal" classification is almost always the status-0 misclassification of a single dropped tile/glyph request, which MapLibre recovers from by itself.
